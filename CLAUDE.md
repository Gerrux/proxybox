# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Язык репозитория — русский: комментарии, доки, сообщения коммитов, строки
журнала и интерфейс. Пишите так же.

## Команды

```bash
pnpm install
cargo run -p pg-service                    # служба (терминал 1); на Linux — без TUN
cargo run -p pg-cli -- doctor              # почему не работает: окружение, не код
pnpm --filter app-shell dev                # фронтенд на :5173, ходит в службу сам
cargo tauri dev                            # окно (только Windows)

pnpm validate                              # tsc --noEmit + vite build + cargo test --workspace
                                           # то же бежит в CI на каждый PR (ci.yml)
cargo test -p core-config vless            # один тест / один крейт
cargo check --workspace --target x86_64-pc-windows-msvc   # windows-ветки без линковки
PG_SINGBOX=/путь/к/sing-box scripts/e2e.sh # сквозная проверка fail-closed
scripts/settings.sh                        # настройки: правка, диск, окружение
```

`src-tauri` — отдельный Cargo-проект (`exclude` в воркспейсе): `cargo
test/check --workspace` его не трогает, собирается он только на Windows.
Тестов-файлов нет, всё в `#[cfg(test)] mod tests` внутри модуля.

Переменные: `PG_SINGBOX` (путь к бинарнику), `PG_TUN=0` (не поднимать TUN),
`PG_PROBE=host:port` (цель пробы), `PG_REFRESH=0` (не сверять подписки сами),
`PG_STACK=system|gvisor|mixed` (чем разбирать пакеты из TUN, по умолчанию
`mixed`), `PG_PPROF=127.0.0.1:48294` (профилировщик sing-box; пусто — выключен).
Последние три, как и `PG_TUN`, настройкой не продублированы: все
диагностические, человеку выбирать там нечего, а включённый по недосмотру
профилировщик — это открытый порт в службе, которая ходит от LocalSystem.
Значение стека уходит в конфиг без
проверки — `sing-box check` имя стека не смотрит, а подстановка умолчания
вместо непонятого значения давала бы замер, который врёт. Остальные
продублированы настройками (`Settings` в контракте) и переменной перебиваются:
окружение сильнее, но на диск не пишется. Состояние — `%ProgramData%\privacy-gateway\`
(на не-Windows — `$XDG_CONFIG_HOME`): `state.json`, `singbox.json`, `singbox.log`.

## Инвариант

Приватный режим включён + туннель не подтверждён = выбранные приложения без
сети. Промежуточных состояний с прямым доступом не существует, bypass-правил
нет. Всё остальное в архитектуре — следствие.

Охватов два: «выбранные приложения» и «весь компьютер» (`Status::all_traffic`).
Инвариант один и тот же, меняется только то, кого он касается.

Правда о судьбе приложения живёт в одном месте — `core_filter::policy()`;
`Tunnel::Down` в статусе означает именно DROP, а не «ошибку».

## Два слоя перехвата

Пока sing-box жив, маршрутизацией занимается он сам: TUN + правила по
`process_path` (`core-tunnel::build_config`). Выбранным приложениям выдан ровно
один маршрут `proxy`, запасного нет; `final: direct` — для всех остальных.

В охвате «весь компьютер» правил по `process_path` нет вовсе: маршрутом по
умолчанию (`final`) становится сам `proxy`. Это не «выбрать все приложения» —
под него попадает и трафик без процесса за ним (служба, драйвер, DNS).

Отсюда и разница в расходе между охватами, а не из перехвата: в TUN под
`auto_route` заходит вся машина в обоих. Одного матчера по процессу где угодно
в наборе правил хватает, чтобы sing-box выяснял процесс **каждому** соединению
машины, и делает он это до разбора правил — порядком и ранним совпадением не
сокращается (проверено на 1.13.19). На Windows это снимок системной таблицы
TCP/UDP плюс открытие чужого процесса. С этим же охватом приходит и жалоба на
`MsMpEng.exe` рядом с sing-box: поток открытий чужих процессов — ровно то, что
разбирает поведенческий монитор Defender. Связь правдоподобна, но не измерена;
разделяется она снятием всех галочек с приложений — правило по процессу тогда не
ставится вовсе, а TUN и `final: direct` остаются на месте.
Дешевле в конфиге не выходит; снимает это только свой WFP-фильтр (потолок
записан в шапке `core-filter`, дизайн — `docs/wfp.md`). Сторож тишины второго
охвата — `all_traffic_takes_the_default_route`.

Пока sing-box не жив, TUN исчезает, и приложения ушли бы напрямую — на это окно
служба ставит блокирующие правила `netsh advfirewall`
(`core-filter::set_blocked`), а в охвате «весь компьютер» —
запрет всего исходящего политикой брандмауэра с одним разрешением для sing-box
(`core-filter::set_killswitch`). Запрещающим правилом это сделать нельзя:
в Windows блокировка сильнее разрешения, и туннелю нечем было бы подняться. Порядок в `Service::start()` обязателен: `guard(true)`
идёт впереди всего, включая убийство старого процесса, а `guard(false)` — только
после подтверждённой пробы в `supervise()`. Менять местами нельзя, это и есть та
самая дыра.

Подтверждает пробу не сам её успех, а совпадение `Service::generation`: порты у
нас постоянные, проба идёт без замка, и за её время туннель успевают
перезапустить — тогда ответ приходит про прошлый процесс и прошлый сервер.

`PROBE_EVERY = 3 с` — период пробы, а ширина окна утечки после падения процесса
— `DEATH_EVERY = 200 мс`: живость стоит одного `try_wait`, проба — похода в сеть,
и связывать их одним периодом значило платить за окно утечки временем сетевого
запроса. Наблюдатель за смертью только запирает и никогда не поднимает туннель
(`the_death_watch_only_blocks`): перезапуском заведует одна ветка `supervise`, и
вторая точка перезапуска — это два sing-box на один TUN и один `singbox.pid`.
Остаток окна закрыл бы свой WFP-фильтр, но ради 200 мс он не окупается — разбор
в `docs/wfp.md`.

## Контракт службы

`core-ipc` — построчный JSON: одна строка запроса, одна ответа (поэтому ответ
обязан быть без `\n` — сторож `single_line`). Транспорт на Windows — только
именованный канал с ACL; отката на TCP там нет намеренно, сокет ограничить
некому. TCP `127.0.0.1:48291` остаётся вне Windows, то есть в разработке.
Клиент открывает канал с `SECURITY_ANONYMOUS`: имя свободно до старта службы, и
подставной сервер иначе получил бы токен клиента. Порты: 48291 IPC (не-Windows),
48292 mixed/SOCKS (проба и headless), 48293 Clash API (счётчики).

Новая команда — вариант `Request`/`Response` в `core-ipc`, ветка в `handle()`
службы и тип в `ui/app-shell/src/platform.ts`. Забыть нельзя ничего: ветку
требует исчерпывающий `match`, а имена фронтенда сверяет с самим перечислением
`the_frontend_speaks_the_same_names` — он же ловит переименование, молчащее с
обеих сторон. Полноту `roundtrip` сторожит он же, изнутри теста.

CLI (`crates/pg-cli`) — по желанию: не всякая команда нужна в консоли, и
`Icon`, `RemoveApp`, `RemoveProfile`, `RemoveSubscription` в ней и не заведены.

Порт службы продублирован ещё и в `ui/app-shell/vite.config.ts` (мост
браузер→служба для разработки без Tauri) — сверяет `the_dev_bridge_knows_the_port`.

Привилегии только в службе. GUI (`src-tauri`) и CLI — тонкие клиенты `core-ipc`
без собственного состояния; логике в них не место. Их зависимости приколочены
храповиком `the_clients_stay_thin`: `core-config` или `core-filter` у клиента —
это разбор чужих ссылок и правила брандмауэра в процессе пользователя. Что уже
позволено (`core-tunnel`/`core-filter` в `doctor`, `core-apps` в оболочке) —
записано в самом сторо́же, новая зависимость роняет его.

## Что легко сломать

- Список приложений и охват правятся только через `Service::edit()`: конфиг
  sing-box перечисляет `process_path` поимённо, а охват держит `final`, и без
  перезапуска добавленное приложение продолжит ходить напрямую под надписью
  «Защищено». Перезапускать или нет, ветки не решают — решение выводится из
  `Service::seen()`, поэтому автообнаружение, добавляющее выключенными, туннель
  не трогает. Сторож — `the_tunnel_restarts_exactly_when_singbox_would_see_another_config`,
  он же следит, что прямых вызовов `reapply` не завелось снова.
  `Service::applied` помнит охват вместе со списком — иначе правила прошлого
  режима остались бы висеть.
- Обновление подписки заменяет профили молча, а активный узел трогает только
  через `after_refresh()`: гасить туннель ради самой замены — значит на миг
  снять правила раньше, чем поднят новый sing-box. Фоновая сверка узел, который
  пропал, не превращает в выключенный приватный режим (`Active::Drop`).
- Всё, что ходит в сеть, разбирается в `handle()` **до** `svc.lock()` — так
  сделана подписка. Иначе окно на все двадцать секунд перестаёт получать статус:
  замок один на состояние и на обработку команды.
- Соединения (`Request::Connections`) служба не хранит и не кэширует: список
  собирается на запрос и умирает вместе с ответом. Кэш «на двух клиентов» — это
  уже хранение трафика, а его продукт не ведёт. Порт clash-api снимается под
  замком, а сам запрос идёт без него: на том конце sing-box, и его молчание
  стоило бы окну всего статуса. Список режется сотней по громкости, поэтому
  утечка обязана ехать впереди неё (`leaks_first`, сторож —
  `a_leak_is_never_truncated_away`): выбранное приложение, ушедшее напрямую, —
  это пара килобайт, и без подъёма оно тонуло бы под чужим торрентом, то есть
  панель теряла бы единственное, ради чего её открывают. Скорость канала окно
  рисует графиком из счётчиков статуса у себя же (`useRates` в
  `StatusBar.tsx`) и держит её на конце канала, а не во вкладке соединений:
  скорость — про сам канал, и смотрят на неё там же, где написано, поднят он
  или перерублен. Полторы минуты в памяти окна — вся история, какая у продукта
  есть; в узком окне остаются числа, в плашке из трея не остаётся ничего.
  Считается она по `Status::traffic_at` — отметке снятия счётчиков, а не по
  такту опроса: служба ходит за ними реже, чем окно спрашивает статус, и те же
  числа, поделённые на две секунды, дали бы нули со всплеском вместо линии.
  Сторож — `the_speed_is_counted_from_the_service_clock`.
- Счётчики трафика забираются раз в `TRAFFIC_EVERY` кругов надзора, а не каждый.
  Clash API отдаёт итоги только в теле `/connections` — вместе со всем списком
  живых соединений и после него, так что оборвать разбор нельзя. Замерено на
  1.13.19: ~357 байт на соединение, 500 соединений — 178 КБ. Под `final: direct`
  через туннель идёт вся машина, и в патологии это десятки мегабайт на опрос
  каждые три секунды: надзор становится усилителем того самого расхода, который
  им же и меряют. Живости это не касается — она на `Process::alive`. Сторож —
  `the_counters_are_not_polled_every_round`. По той же причине ЦП меряют с
  закрытой панелью соединений: открытая опрашивает то же тело каждые 2 секунды.
- `Service::applied` помнит применённое к брандмауэру: без этой памяти надзор
  дёргал бы `netsh` каждые три секунды. Неудачу не запоминаем намеренно.
- Настройки службы приходят набором целиком (`Request::SetSettings`), и клиент
  присылает обратно то, что ему показали, — то есть уже перебитое окружением.
  Поэтому `handle()` возвращает перебитые поля к сохранённым: без этого
  `PG_PROBE`, выставленная в e2e, записалась бы в `state.json` навсегда с первой
  же правки любой другой настройки. Действующее живёт в `status.settings`,
  выбранное человеком — в `Service::settings`, и путать их нельзя.
- Ни одна настройка не проходит через `Service::reapply()` — и не должна: путь к
  sing-box действует со следующего запуска, проба и страна со следующего
  измерения, сверка со следующего круга. Это единственные команды, меняющие
  состояние без перезапуска туннеля, и причина ровно одна: перезапуск ради
  настройки — это выбранные приложения без сети на ровном месте.
- Раскладка окна держится на трёх классах в `index.css` (`.panes`, `.pane`,
  `.pane-on`) и трёх порогах: до 1100 px показана одна панель из трёх, до
  768 px приборная линейка сжимается в строку, до 470 px ужимается и остальная
  шапка (плашка из трея). Правила лежат нелоенным CSS
  намеренно — они спорят за `display` с утилитами Tailwind, а `@layer
  utilities` проигрывает нелоенному всегда, независимо от порядка в файле.
  Тем же порогом 470 px живёт `minWidth: 380` в `tauri.conf.json`: поднимут
  минимум обратно — и половина этих правил станет мёртвой.
  Средний порог — не вкусовщина: пятиколоночная сетка линейки помещается ровно
  с 768 px, а промежуточные сетки из двух и трёх колонок уносили счётчики
  трафика на второй-третий ряд, а его — за нижний край окна. Строка эта
  переносам не подлежит вовсе, ужимаются только имя профиля и название страны;
  сторож — `the_instrument_row_never_wraps`.
- Окно рисуется без системной рамки (`decorations: false`): титульную полосу и
  три кнопки рисует `ui/app-shell/src/TitleBar.tsx`. Перетаскивание держится на
  голом `data-tauri-drag-region` (атрибут на предке отдал бы под drag и кнопки)
  и на правах `core:window:allow-*` в `src-tauri/capabilities/default.json` —
  без них вызовы молча отклоняются, и окно нельзя ни сдвинуть, ни закрыть.
- Ошибку в окне ставит только команда, а опрос статуса её больше не снимает
  (`App.tsx`): сразу за командой идёт перечитывание статуса, и «успех» от него
  стирал бы сообщение через миллисекунды — битая ссылка исчезала бы бесследно,
  потому что разбор ссылки служба в журнал не пишет. Снимают ошибку крестик и
  следующее действие.
- Закрытое окно прячется в трей, а не гасит оболочку: служба держит туннель и
  правила и без окна, и в охвате «весь компьютер» закрытое окно оставляло бы
  запертую машину вообще без следа в интерфейсе. Прятать можно только тогда,
  когда значок действительно создан, — за этим и следит `TRAY` в
  `src-tauri/src/main.rs`; без флага неудавшийся значок делал бы приложение
  невидимым и незакрываемым.
- Окон в оболочке два: `main` и `tray` (плашка). Всё, что оболочка шлёт
  фронтенду, идёт через `emit_to("main", …)`: `emit` рассылает событие всем
  окнам, и плашка получила бы чужой крестик (сторож —
  `the_shell_never_calls_from_its_event_loop`). По той же причине у неё своя
  запись в `capabilities/` — `default.json` перечисляет окна поимённо, и новое
  окно без своей записи не получает вообще ничего.
- Плашка гаснет по потере фокуса, а клик по значку фокус и уводит: без отметки
  `HIDDEN_AT` тот же клик, которым её закрывают, открывал бы её заново. Триста
  миллисекунд — это не «на глаз красиво», это окно между гашением и приходом
  события клика.
- Значок трея и его меню пересобираются только при смене `signature()`:
  перестроенное меню закрывается под рукой, а `set_icon` каждые три секунды —
  мигание в панели задач. Добавили в меню поле статуса — добавьте его и в
  отпечаток, иначе оно замрёт навсегда.
- Обработчик меню значка крутится в цикле событий, поэтому любой поход в службу
  оттуда идёт своим потоком (`detached`). Синхронный `call` там — это то же
  «не отвечает», что и синхронная `#[tauri::command]`.
- Команды `src-tauri` — только `#[tauri::command(async)]`: синхронную команду
  Tauri выполняет в цикле событий главного потока, а `core_ipc::call`
  блокирующий, и окно не разбирает очередь сообщений, пока служба отвечает
  секундами. Компилятора у оболочки нет вовсе (она вне воркспейса), поэтому
  сверяет текстом `the_shell_never_calls_from_its_event_loop` в `core-ipc`.
- Процессы оболочка запускает только через `quiet()`: без `CREATE_NO_WINDOW`
  Windows даёт консольной программе собственное окно, и `reg`, которым панель
  настроек читает автозапуск, мелькал чёрным прямоугольником на каждое её
  открытие. Сторож — тот же `the_shell_never_calls_from_its_event_loop`: он
  считает `Command::new` в оболочке, и их ровно один.
- Версия приложения — только `src-tauri/tauri.conf.json`. Оттуда её берёт окно
  (`vite.config.ts` подставляет `__APP_VERSION__`), с ней же сверяется тег в
  `release.yml`, и по ней окно решает, вышло ли что-то новее. Разъедется с
  тегом — установленное приложение будет считать себя устаревшим всегда.
- Прогон профилей (`Request::TestProfiles`) поднимает свой sing-box — без TUN,
  на портах из `free_port()` и в подкаталоге `probe/`. Общий каталог с живым
  туннелем означал бы, что прогон добивает его по `singbox.pid`; общие порты —
  что он вообще не стартует. Замок на время прогона отпущен: он длится секунды.
- Браузерный профиль — не узел: `Status::browser_profiles` хранит имя, узел, UA
  и язык, а сеансы (`Service::browsers`) заводятся по имени браузерного профиля.
  На один узел их бывает несколько, и удаление узла гасит сеансы всех, кто на
  него смотрел (`stop_sessions_on`), но сами профили оставляет: в их каталогах
  лежат входы человека, и починка — это выбрать другой узел, а не завести всё
  заново.
- Цвет браузерного профиля считает окно (`profileColor` в `ui.tsx`) и передаёт
  оболочке строкой: тем же цветом рисуется точка в списке и значок окна в панели
  задач (`core_apps::icon_bytes`). Посчитанный в Rust второй раз, он разъехался
  бы на первой правке палитры — и стал бы врать про то, какое окно чьё.
- Win32 для окна браузера живёт в `core-apps`, а не в оболочке, намеренно:
  `src-tauri` вне воркспейса, и `cargo check --workspace --target
  x86_64-pc-windows-msvc` его не трогает. Небезопасные вызовы, которые нигде не
  компилируются, кроме живой Windows, — плохая сделка.
- Личность окна делается ровно тремя вещами: `--user-agent`, `Accept-Language`
  через `Preferences` каталога сеанса и адрес узла. Всё остальное из карточки
  антидетект-браузера (canvas, WebGL, часовой пояс, число ядер, `Sec-CH-UA`)
  флагами не подделывается — только патченным Chromium. Не добавляйте полей,
  которые ничего не делают.
- Каталог у сеанса браузера свой (`browser/<dir_name>`), и имя ему считает
  `core_ipc::dir_name` — одна функция на службу и на оболочку. Голой чистки
  символов мало: «a/b» и «a-b» дали бы один каталог, а каталог сеанса — это его
  `singbox.pid`, по которому `Tunnel::start` добивает предшественника. Два
  профиля молча гасили бы друг друга, как гасил каждый новый сеанс, пока
  каталог был общий.
- Установщик гасит службу до копирования файлов
  (`NSIS_HOOK_PREINSTALL`): Tauri закрывает только своё окно, а `pg-service.exe`
  и `sing-box.exe` остаются занятыми — NSIS упирается в них на `File` и
  показывает «Error opening file for writing» вместо обновления. Гасим `net
  stop`, а не `sc stop`: второй возвращается на STOP_PENDING, когда файлы ещё
  заняты. Удалять службу на этом шаге нельзя — см. следующий пункт.
- `service::install` остаётся идемпотентной: установщик зовёт её при
  каждой установке, а служба к этому моменту уже может быть в SCM. Голый
  `create_service` отвечает ERROR_SERVICE_EXISTS — и обновление поверх выглядит
  как провал установки при полностью исправной службе.
- Тип узла из JSON или подписки сверяется с белым списком `core_config::NODES`,
  и это не вкусовщина: профиль `{"type":"direct"}` стартует, пробу проходит,
  служба снимает блокировку — и трафик идёт в открытую сеть под «Защищено».
  Чёрный список служебных outbound'ов этого не ловил: голый объект шёл мимо него.
- Подписка качается только по `https`, и проверка стоит в `fetch()`, а не в
  разборе команды: тем же путём ходит плановое обновление, а адрес мог
  сохраниться в `state.json` раньше проверки.
- Журнал пишется на диск (`journal.json`) каждой строкой и переписывается
  целиком — тридцать строк, три килобайта. Значит, логировать в цикле нельзя:
  дедупликация повтора в `write_log` держит не только ленту, но и диск.
- `Status::refreshed_at` двигает только удачная сверка, и по нему же считается
  срок следующей. Начнёте отмечать им попытку — плановая сверка перестанет
  случаться вовсе: недоступная панель будет откладывать сама себя.
- Уведомление в оболочке говорит о переходе `Up → Down`, а не о состоянии, и
  только при невидимом окне. Добавите сюда `Connecting → Down` — получите тост
  на каждый круг перезапуска, то есть раз в минуту при недоступном сервере.
- Имена разрешает сервер (`dns.final: remote`, `detour: proxy`), и держится это
  на трёх вещах сразу — убрать можно любую и получить ту же петлю.

  Первое: секция `dns` обязана быть. Без неё запрос уходил системному резолверу,
  попадал под маршрут по умолчанию и возвращался в тот же TUN — полтора ядра,
  девять десятых времени в ядре, полсотни «соединений» в секунду при пустом
  трафике.

  Второе: DNS машины обязан **перехватываться**
  (`{"inbound":["tun-in"],"port":[53],"action":"hijack-dns"}`). Секцию завели, а
  перехват — нет, и петля вернулась в другом виде: `sing-tun` под `auto_route`
  сам прописывает адаптеру DNS-сервером адрес шлюза (`Inet4Address[0].Next()`),
  Windows шлёт запросы туда, а ждать их некому — запрос становится обычным
  соединением, уходит в `final`, и на `direct` sing-box отбивает его мгновенно
  как петлю в свою же подсеть. Замер на живой машине: 1025 соединений из 1047 на
  `172.27.234.2:53`, сеть 0 Мбит/с, ЦП 85% (sing-box 45%, NisSrv 16% и гигабайт
  памяти под ней). Только на `tun-in`: вход `local` — путь пробы. Сторож —
  `the_machine_dns_is_hijacked_on_the_tun_only`.

  Третье: адрес самого сервера разрешается мимо туннеля
  (`default_domain_resolver: local`) — чтобы спросить `remote`, нужен уже
  поднятый `proxy`. Но `local` обязан быть назван **адресом и по DoH**, а не
  `type: local`: системный резолвер после `auto_route` — это адрес нашего же
  шлюза, то есть ссылка на себя, а с перехватом — замкнутый цикл. Стоит
  `https://8.8.8.8` — тот же резолвер, что у человека на адаптере, и
  шифрованный, потому что открытый UDP показал бы имя сервера сети по пути.
  `detour` у него нет и быть не должно: `detour: "direct"` на нашем пустом
  `direct`-outbound — это отказ старта («detour to an empty direct outbound
  makes no sense»), причём `sing-box check` его пропускает. Сторожа —
  `names_are_resolved_by_the_server_but_the_server_is_not` и
  `the_config_actually_starts`.
- Конфиг обязан не только разбираться, но и запускаться, и это разные проверки.
  `sing-box check` смотрит разбор; отказы вроде `detour` на пустой outbound
  вылезают только при `run`. Поэтому рядом с `*_passes_singbox_check` стоит
  `the_config_actually_starts` — он поднимает настоящий sing-box без TUN на
  свободных портах. Одного `check` мало: этим и пропустили конфиг, который не
  стартовал.
- Сниффинг обязан висеть только на `tun-in`. Со `sniff` sing-box отвечает
  входящему раньше, чем дозвонится наружу: он ждёт первых байтов, чтобы прочитать
  имя. Проба же считает подтверждением ответ на свой SOCKS-запрос — накрой
  сниффинг вход `local`, и мёртвый узел станет подтверждённым туннелем, а
  `guard(false)` снимет блокировку. Сторож — `the_probe_path_is_never_sniffed`;
  первым это поймал `measure_fails_on_a_dead_node`.
- Ошибки TUN почти всегда означают не то, что написано: `explain()` переводит
  их в «нет прав администратора» или «рядом чужой туннель».
- Адрес TUN `172.27.234.1/30` и имя «Privacy Gateway» выбраны против умолчания
  sing-box (`172.19.0.1/30`), которое одинаково у NekoBox, Hiddify и v2rayN.
- Шлюз TUN (`172.27.234.2`) отбивается первым правилом маршрутизации, и это не
  украшение. Своим его никто не назначает — `sing-tun` выводит его как
  «следующий за нашим», — и отвечать по нему некому, а приложения исправно его
  опрашивают (SSDP на 1900, NAT-PMP на 5351, так ищут роутер). Без отбоя запрос
  уходит в маршрутизацию: на `direct` sing-box отбивает его сам и мгновенно, а
  приложение повторяет тут же — шторм, упирающий ядро в потолок при пустом
  трафике; на `proxy` тот же запрос стоит целого RTT, и повторов на три порядка
  меньше. Отсюда и разница в расходе между охватами, которую долго списывали на
  объём трафика. Отбой обязан быть молчаливым (`method: drop`): обычный `reject`
  отвечает ICMP unreachable, то есть так же мгновенно, и шторм от него не
  прекращается — дешевеет лишь каждая итерация. И порт 53 обязан оставаться
  снаружи отбоя: под `auto_route` `sing-tun` прописывает адаптеру DNS-сервером
  этот же адрес (`Inet4Address[0].Next()`), так что безусловный отбой снёс бы
  разрешение имён всей машине — тише, чем шторм, и куда хуже. Кто именно
  обслуживает пришедший туда запрос, на живой Windows не проверено; пока не
  проверено — не трогаем. Константы связаны сторожем
  `the_gateway_is_next_to_our_address`, само правило — `the_tun_gateway_is_rejected_first`.
- Раскладка полей узла повторяет NekoBox; WireGuard в схеме sing-box 1.13 живёт
  в `endpoints`, не в `outbounds` — `build_config` различает по `type`.

## Стиль

Правило со словом «обязан» заводится вместе со сторожем, и абзац ссылается на
него по имени теста; без сторожа оно не соблюдается — проверено. Прозой живут
суждения и размены, а не правила.

Комментарии объясняют «почему», а не «что»; шапка модуля — рационал целиком.
Сознательное упрощение с известным потолком помечается комментарием
`ponytail:` с указанием потолка и пути апгрейда — их девятнадцать, они настоящие,
не выдумывайте новых и не удаляйте молча.

TS strict во фронтенде. Наружу не уходит ничего: ни телеметрии, ни логов
трафика; проба по умолчанию идёт на сервер самого пользователя.

Раздел README «Чего ещё нет» — актуальный список известных дыр (в том числе:
ничего не проверено на живой Windows; канал различает пользователя, но не
программу; `%ProgramData%` наследует чужие права). Держите его в курсе, когда
закрываете пункт.
